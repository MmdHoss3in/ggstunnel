# v0.3.1-rc2 field performance repairs

The supplied field logs show FAST in Iran and COMPAT at the foreign endpoint, with no confirmed foreign FAST ACK reception. Iran emitted 82,066 PULL probes versus 55,407 FAST DATA frames in an 18-second interval. These are directional control/data transmission counts, not a PULL response ratio. The operator reports concurrent Xray users and that neither menu option 16 nor 21 had been applied.

## Implemented changes

The old actor derived adaptive PULL rate from all received payload frames. Successful FAST/COMPAT reception could therefore pay for more polling even when that polling path did not return DATA. The repaired actor requires an authenticated PULLED EchoReply matching an outstanding local ICMP tuple. Only newly retained DATA contributes to growth; duplicate responses cannot multiply yield. All DATA keeps the existing authentication, anti-replay and ordered acceptance rules.

Request memory is bounded to four negotiated receive windows (at most 32768 tuples), independently of the reliable DATA flight. Empty probes awaiting expiry must not consume all request capacity and impose an accidental low throughput ceiling. Unanswered requests expire after max(1s, response grace); expiry affects feedback, not acceptance of late DATA. Response grace is max(500ms, four times measured PULL RTT, four times available DATA ACK RTT). Active polling halves after grace without a response, down to 50pps; the independent configured idle probe remains. Valid returned DATA restores growth. Local FAST health does not suppress the opposite direction's need for PULL. Adaptive unlimited_rate can exceed the configured max_pps when genuine returned DATA supports it; bounded flight, memory, scheduling bursts and congestion control remain.

The first A/B run also exposed repeated delivery-budget recovery in the asymmetric case. Retries used EchoRequest even while FAST EchoReply transmission was confirmed healthy; that request direction was deliberately blocked. Retries now use the confirmed FAST direction while it remains valid, retaining pacing, congestion cuts, retry limits and tuple-assisted fallback. A regression blocks all such originated requests and peer PULL rescue, drops one DATA frame and requires ordered completion using FAST retries.

SACK reordering grace now starts when distinct delivery evidence arrives, rather than already expiring during the preceding RTT. Retry attempts still respect their send-time guard and frozen RTO deadline. A briefly reordered original can arrive during this grace and remove its pending retry without a retransmission or congestion cut. A late-feedback regression is required to fail on rc1. Raw socket shutdown also waits for the actor before closing the nonblocking sender descriptor, preventing descriptor reuse during an in-flight send.

Originated response controls of type EchoRequest now allocate a local tuple, while EchoReply responses mirror the requesting peer tuple. This avoids reusing the peer's identifier/sequence for a new opposite-direction request and supports a strict per-tuple one-reply appliance model. Linux conntrack itself keys ICMP by identifier and allows duplicate replies, as [the kernel implementation](https://github.com/torvalds/linux/blob/master/net/netfilter/nf_conntrack_proto_icmp.c) shows. These changes do not claim support for NAT that rewrites authenticated ICMP identifiers.

Each new engine stats sampler starts at current inner/outer totals. Lifetime counters survive transport recovery, while first-interval rates include only new traffic. Telemetry adds valid PULL response/yield, outstanding/expired requests and budget, control versus DATA wire bytes and real socket buffer sizes. Linux SO_RCVBUF/SO_SNDBUF values include doubled accounting; they are not comparable one-for-one to the requested value.

Option 21 additionally requests at least 4MiB BIP socket buffers, preserves larger requests and other transports, saves configuration backups and restarts active services. Option 16 raises host ceilings to at least 16MiB while preserving higher settings. Run 16 before 21, or restart after 16 if 21 was already applied. Installing an updated binary preserves explicit old configuration, and opening the menu does not rerun dependency checks.

Short MORE/NEED_PULL gaps retain a recently confirmed receiving rate instead of resetting every burst to 1000pps. A recent PULL-delivered flight can keep return tuples available for inner ACK traffic. Stale receiving rates still restart conservatively, and unanswered discovery remains bounded.

Cloud CPU profiles exposed repeated HMAC setup, full DATA copies and per-packet socket calls. The actor now reuses independent master/session HMAC state, replacing cached state when keys change, and encodes directly into a single IPv4 buffer. MAC inputs, wire authentication and encryption counters remain unchanged. Native Linux amd64/arm64 receive uses nonblocking recvmmsg with up to 16 datagrams and runtime polling/deadlines; scalar receive remains available if unsupported. Earned PULL probes and already prepared DATA use sendmmsg batches of at most 64. DATA batches flush within the current actor event, at the size bound, or before a control send; input draining never waits to fill a batch. Successful-prefix accounting prevents unsent requests from funding feedback or inflating wire counters, and unsent DATA retains its reliable pending entry for ordinary paced retry. No DagMux or independent stream multiplexer is added.

CLI-generated samples (-gen server/client) now match the installer examples for unlimited adaptive scheduling, 8192-frame queue, 128-frame scheduling burst, eight retries and 1024-packet TUN queue. Existing explicit configurations still require option 21 to adopt this recipe.

Completed native receive batches now enter the actor as one bounded event (at most 16 datagrams). The reader no longer wakes the actor with the first packet before enqueueing the rest, which could defeat reply batching. Queues remain bounded and packets are copied before reuse of receive storage; no additional input is awaited. Persistent-hole recovery uses the cheaper of advertised SACK offsets and retained pending entries, instead of scanning an entire wide flight for a narrow ACK range. Retry age/evidence guards, frozen deadlines and sequence-zero wrap handling remain tested.

Small-frame packing is negotiated with READY offer/acknowledgement payloads authenticated for the already verified active peer and current local identity. Existing READY flags and PROOF payloads remain unchanged so old peers ignore the offer and retain ordinary DATA. New native peers can use an authenticated DATA packed flag after acknowledgement. Up to 16 already queued sealed frames fit into one bounded outer payload, using count/length framing. No new input is awaited; one retained lookahead preserves FIFO when a frame cannot fit. Original AEAD ciphertext, nonce, identity and replay sequence remain byte-identical. Receive lengths/counts are checked before retaining/ACKing DATA or consuming PULL correlation; partially drained bundles remain owned until every inner frame is emitted. Retries preserve the packed flag. Peer identity changes clear capability and receive metadata. peer_packet_packing and packed_data/frames counters expose use. For a controlled comparison, a systemd override with `Environment=GGS_BIP_PACKET_PACKING=0` and restart disables advertisement; the opposite peer then retains ordinary DATA too.

## Short cloud validation

No local Go/Python tooling or reference binary is executed. Tests run on disposable GitHub-hosted Linux amd64 and arm64 runners.

- The actual engine sampler restarts with 8GiB TX/70GiB RX historical traffic, then measures controlled new increments in two epochs. The same regression is required to fail on rc1, with its expected historical-rate error, before accepting repaired sampling.
- Repeat asymmetric bidirectional transfer under race detection; verify ordered, uncorrupted DATA in both directions and low unanswered polling despite unrelated successful payload reception.
- Require both the strict per-tuple handshake and blocked-request FAST retry regressions to fail on rc1 before accepting repaired behavior. Test authenticated/matched/unique response feedback separately from tampering, replay and unmatched late DATA delivery.
- Real TUN A/B: rc1 versus candidate, 80ms RTT, 200/500Mbps links, forward/reverse, 16 inner TCP streams, 2s warm-up and 10s measured traffic. Each sample starts fresh endpoints. Reverse samples alternate version order. Retain all observations and errors.
- Cases: clean; Iran request kinds 1-6 filtered while authenticated bootstrap and reply DATA pass; router conntrack rejecting unsolicited EchoReplies with FAST probes additionally blocked so both versions exercise PULL; and independent 8000pps directional policers including all ICMP control/retry/DATA. Host receive/send ceilings are raised to at least 16MiB for both A/B binaries, matching the user's planned option 16.
- Candidate clean, asymmetric and stateful transfers require >=100Mbps on 200Mbps links and >=200Mbps on 500Mbps links. Clean/stateful A/B drops >35% fail. PPS-policed cases require >=30Mbps. Asymmetric unanswered Iran polling must average <=200pps across the whole measured operation including startup. Stateful transfers must actually receive PULLED DATA. Process PIDs must remain unchanged with no internal recovery; additional state is retained in artifacts.
- The initial stateful harness incorrectly disabled kernel ICMP echo globally, which also disabled inner TUN ping while authenticated DATA still passed. Both rc1 and candidate therefore failed its ping-based startup check. That harness error is corrected; these failed observations remain retained and are not evidence of a failed bootstrap.
- Resource snapshots retain process CPU seconds, effective host CPU allocation and router qdisc packet/drop counters. Separate CPU-instrumented builds and larger-queue experiments are diagnostic evidence only; they do not certify the release executable or replace exact-source gates.
- Full tagged-source race/audit, fuzz, raw socket/TUN, manager/installer/systemd, five-carrier, compatibility, capacity and resource gates remain required before release creation. Raw new field results are attached separately to the release.

These short synthetic checks cannot predict multi-day survival on a different provider path with 95% confidence. Field feedback still determines whether this specific Iran/foreign deployment benefits.

## Reference interpretation and subsequent protocol work

The candidate automatically adds an instance-tagged iptables OUTPUT rule scoped to the configured outer IPv4 pair, EchoReply type, BIP5 magic and kinds 3/4/7. These are redundant kernel copies of originated PULL/NEED_PULL/HELLO requests. DATA/ACK/FAST and ordinary ping pass. Normal close deletes that exact rule; the installed systemd unit also invokes `-cleanup-bip-echo` in ExecStopPost after abnormal termination. Missing iptables/u32 support logs a warning and leaves the transport operational, with `kernel_echo_filter=false`. No chain flush or global ICMP suppression is performed. Cloud scope tests exercise both endpoints, another outer peer, unrelated rules, inner ping and normal/SIGKILL cleanup. Exact-source field gates require the filter to be installed and retain endpoint rule counters.

[Dagger's own README](https://github.com/itsFLoKi/daggerConnect) advertises a proprietary DagMux core. It does not publish enough implementation detail here to conclude that DagMux is a modified SMUX, or that its TUN uses the same stream multiplexer. Compiled legacy SMUX/KCP symbols and installer values are evidence of capabilities/configuration, not active algorithms. GGSTunnel adds no SMUX dependency and does not claim to copy DagMux.

Backhaul's 8-way MUX, 4MiB session receive buffer and 2MiB stream buffers, and Dagger's resource profiles, motivate independent flow budgets and bounded scheduling. Their stream frame sizes and pool count must not be copied as raw ICMP MTU or eight conflicting TUN interfaces.

Independent authenticated delivery lanes, a shared aggregate wire budget, pre-encryption queue age control and confirmed outer MTU discovery remain subsequent work. Each needs compatibility, loss/reorder, memory/replay and cryptographic nonce tests before activation. The current reliable BIP ordering can still block unrelated inner flows while recovering a missing frame, and delivery-budget recovery can interrupt application connections.
