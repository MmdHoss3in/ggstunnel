# Directional ICMP control return path

An overlapping field capture showed 538 PULL requests and 11 FAST acknowledgements leaving Iran as ICMP EchoRequests, with none present at the foreign capture. Both directions' EchoReply probes arrived, as did nearly all DATA. Eight missing foreign EchoRequest DATA packets arrived after retransmission. This locates the observed absence between capture points, without identifying a particular firewall. The complete local forensic record is retained outside the repository; user packet captures, addresses, keys and session identities are not published.

The old FAST probe used EchoReply and its response used EchoRequest. Consequently a working EchoReply DATA path could not be confirmed when the response direction's EchoRequests were blocked. The same problem would affect standalone ACKs after switching to FAST, particularly for one-way UDP without application ACKs.

The candidate first keeps the original probe/response behavior. After an unanswered attempt, the next paced probe requests an additional EchoReply FAST_ACK using MORE in the FAST_PROBE kind only. Its random token and fixed expiry are unchanged, and its tuple/counter/MAC are fresh. The traditional response is retained. The receiver never treats the request itself as proof that its own outgoing FAST path works. Only its own live token returned by the authenticated active peer can prove that direction.

An authenticated request for the alternative gives DATA ACKs a finite-lived EchoReply return preference. Dedicated ACKs also attempt the traditional EchoRequest as a transition safety net; successful DATA piggyback avoids those dedicated packets. Either successful socket send can finish an ACK emission attempt; failing both retains the ACK deadline. This is not proof of network delivery: normal retransmission/SACK recovery remains necessary. Request DATA still receives a paired EchoReply ACK. A fresh unhinted probe clears the peer preference, and a successfully returned traditional FAST_ACK restores ordinary probing. Identity rotation clears all local path preferences without resetting existing telemetry counters or reusing keys/nonces.

Old peers ignore the reused FAST_PROBE flag and keep their previous behavior. Normal mixed-version operation stays compatible; repairing a blocked return direction requires the responding peer to support the change, so upgrade both endpoints. Legacy and compact remain incompatible wire choices and must be configured together. The existing legacy/compact echo filters allow real local responses; no filter scope is changed by this patch.

Unanswered active PULL discovery now continues at 5pps after max(5 seconds, ten response grace intervals), rather than staying permanently at 50pps. The independent periodic probe remains. A verified correlated returned DATA frame restores polling growth. Empty requests, unrelated FAST/compat DATA, duplicates and kernel echoes cannot fund polling.

The validation models include blocked EchoRequests on either side, legacy and compact, one-way payload delivery with a fully retired flight, live-token expiry/replay/MAC checks, ACK socket failures and paired tuples, normal stateful/request fallback regressions, and 100/200Mbps real TUN TCP/UDP. Loss samples report useful throughput with the existing 1Mbps connectivity floor; they do not claim repaired global ordering or multi-day reliability. No congestion bounds, ACK integrity or release acceptance criteria are disabled.

After a successful release, upgrade the foreign endpoint first and then Iran using the pinned installer. Existing configurations are preserved. If options 16/21 have already been applied, repeating them is not required for this control-path fix. Check `fast_healthy`, `tuner.path_mode`, `reply_control_rx`, pending/backlog, new drop deltas and internal recoveries on both endpoints. `reply_control_rx` can remain zero on a normal path; it counts fresh FAST confirmations through the alternative, not all EchoReplies.
